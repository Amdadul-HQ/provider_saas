# Sprint 1 — Security review (security-expert)

Date: 2026-10-29 · Scope: `backend/` + `frontend/` at end of Sprint 1. Read-only review: no code was changed.
Method: line-by-line reading of platform/auth, vault, db, httpx, gql, webhooks, every `repository.go`, the public storefront/portal
resolvers and the frontend storefront/auth code. Scripted checks covered every DB call missing `tenant_id` and every Query/Mutation
field missing `@auth`. Live probes against the running API on :8080 were limited to read-only requests or requests with wrong
credentials: aliased logins, `/uploads` traversal, CORS preflight. I checked the DB role with `pg_roles` and ran `govulncheck` and `pnpm audit --prod`.

**Verdict: NOT ready for production.** No Critical findings. There are 6 High findings: RLS does not work, viewer/reseller roles can change data,
credentials are stored in plaintext in the inbox, SMS payment verification can be spoofed, inbound messages can be hijacked across tenants,
and login can be brute-forced. All six must be fixed or accepted with an ADR before the Sprint 1 security sign-off.

### Verified controls (no finding)
- **Repository tenant scoping**: a script checked every `Query/QueryRow/Exec` in `internal/**`. Every call on a tenant table filters by `tenant_id` and runs inside `db.WithTenantTx`. The only queries without a tenant filter are intentional platform-level ones: `users`/`refresh_tokens` (`auth/repository.go`), `tenants` lookups, `social/repository.go:54,61,102` (webhook routing, see H5), `storefront/repository.go:38` (public slug), `storefront/repository.go:154` (portal token hash) and `jobs`. Services check foreign ids against the tenant before writing (customers, products/plans, slots, social accounts for posts, invoice/payment links, conversation assignee membership), except the gap in L4.
- **Dataloaders** (`backend/graph/loaders.go:59-68`) are created per request and every entity/batch loader is tenant-scoped through `tenantOf(ctx)`. The `User` loader is not tenant-scoped, but it only receives ids taken from tenant rows. `User.memberships` is limited to self or platform admin (`graph/auth.resolvers.go:91`).
- **Public resolvers**: `publicStorefront` returns only published storefronts and active products/plans, with no cost, supplier or stock counts (only `inStock`). `portal` stores only the SHA-256 of a 256-bit token and checks expiry; `portalRequestRenewal` verifies `sub.CustomerID == token customer`. The portal shows the masked `deliveryNote`. `placeOrder` validates input, has a per-client limiter (weakened by M1) and rejects reused TrxIDs.
- **@auth coverage**: the fields without `@auth` are `health`, `register`, `login`, `refreshToken`, `logout`, `publicStorefront`, `publicOrder`, `portal`, `placeOrder` and `portalRequestRenewal`. All are meant to be public. OWNER-only: `updateMemberRole`, `removeMember` (last-owner protection present). Owner/Admin: credential set/reveal, social connect, storefront, catalog/inventory writes, `auditLogs`, `voidInvoice`, ledger adjustments. `inviteMember` refuses `owner`.
- **Passwords**: argon2id with t=3, m=64 MiB, p=2, 16-byte salt, 32-byte key, constant-time compare, and a dummy hash for unknown users.
- **JWT**: HS256 pinned through `WithValidMethods` (no `alg` confusion or `none`), issuer checked, `exp` required, secret ≥32 bytes. Refresh tokens are 256-bit random values stored as SHA-256, rotated on every use. Reuse revokes all of the user's sessions, and a password change revokes all of them too.
- **switchTenant** checks membership and rejects disabled members (status gaps are covered in M4 and L2).
- **Vault**: AES-256-GCM, a fresh 96-bit random nonce per seal, key version stored, tenant bound through AAD. `Reveal` is OWNER/ADMIN-only and writes `audit_logs`. `Open` is used only by machine paths (social tokens, the SMS token compare, delivery, which writes its own `delivery.render` audit). The tenant `settings` output removes `sms_webhook_secret_id`. The delivery note on subscriptions masks the password and PIN.
- **Webhooks**: Meta uses HMAC-SHA256 over the raw body with `hmac.Equal`, reads at most 1 MiB before the check, and rejects an empty app secret. The verify-token check, the Telegram per-account derived secret and the SMS bearer token (vault, tenant-prefixed) all use constant-time compares. SMS bodies are capped at 64 KiB. Ingest is idempotent on the external message id. Meta does not sign timestamps, so idempotency is the replay control.
- **Injection**: no SQL is built from user input. `fmt.Sprintf` only builds `$n` placeholders or constant fragments (`customer/repository.go:216` table names come from the fixed `mergeTables` list; `inbox/repository.go:128` is a constant). `ORDER BY` is never taken from user input.
- **Uploads**: `http.Dir` blocks traversal (probed live: `..%2f`, `%2e%2e`, backslash → 404), directory listing is off, nosniff is set, and only server-generated PNGs are written, under `uploads/<tenant>/`.
- **CORS**: an explicit origin allowlist; a preflight from a foreign origin got no `Access-Control-Allow-Origin` (live). Auth uses a bearer header, so cookie CSRF does not apply.
- **Introspection and playground** run only in dev (but see M5). In non-dev, unknown errors are masked as `INTERNAL_SERVER_ERROR`. The service worker never caches API responses. The portal route sends `Referrer-Policy: no-referrer`.
